Repository: mas-bandwidth/netcode.rs, branch
`sprint/rs-netcode-port-matches-the-c-reference.w1.g1.e20` at
`25d97ccccc89448d7f6e4be4f0b1790b3e49166a`, from `sprint/netcode-rs-port`.

No C checkout is reachable from this job (JOB.md names none, `NETCODE_C_DIR`

## 1. Wire format

**MATCH.** Compared `src/packet.rs`, `src/bytes.rs`, `src/crypto.rs` against
STANDARD.md sections "Connect Token", "Packets" and "Reading Encrypted
Packets", and against the golden vectors read by `src/wire_compat.rs`.

- Seven packet types 0..6: packet.rs:17-24, `packet_type()` packet.rs:58-68.
- Request packet is `1 + 13 + 8 + 8 + 24 + 1024 = 1078` bytes:
  packet.rs:26-27, written packet.rs:124-135.
- Prefix byte = low 4 bits type, high 4 bits sequence-byte count:
  packet.rs:143, decoded packet.rs:262/274.
- Sequence bytes in `[1,8]`, high zero bytes omitted, low byte first:
  `sequence_number_bytes_required` packet.rs:100-102, write packet.rs:150-151,
  read packet.rs:274-288.
- Nonce = four zero bytes then the sequence as 64-bit little endian:
  crypto.rs:19-23 (pin test crypto.rs:156-161).
- Packet AEAD associated data = version info, protocol id, prefix byte:
  packet.rs:106-113.
- Response/challenge body = 8-byte sequence + 300-byte challenge data:
  packet.rs:338-352; keep-alive 8 bytes packet.rs:354-360; payload
  `[1,1200]` packet.rs:362-368; denied/disconnect 0 bytes packet.rs:330-335,
  370-376.
- Address type 1 = IPv4, 2 = IPv6: bytes.rs:8-9, 58-73, 116-133.
- Golden vectors pin every writer and reader byte-for-byte: wire_compat.rs
  (packet, token and challenge vectors), `tests/vectors/*.bin`.

## 2. Replay protection

**MATCH.** Compared `src/replay.rs` and the read order in
`src/packet.rs:read_packet` against STANDARD.md "Replay Protection" and
IMPLEMENTERS.md section 1.

- Window 256: replay.rs:9 (`REPLAY_PROTECTION_BUFFER_SIZE = 256`).
- Overflow-safe subtraction-side compare: replay.rs:31-35; regression test

- Replay test runs before decrypt (packet.rs:294-303) and the window is
  advanced only after a successful decrypt (packet.rs:311-322). This is the

- `u64::MAX` sentinel for an empty slot: replay.rs:11.

## 3. Connect token

**MATCH.** Compared `src/token.rs`, `src/lib.rs` and `src/server.rs` against
STANDARD.md "Connect Token" / "Challenge Token".

- Public token 2048 bytes (lib.rs:112), private 1024 (token.rs:18), challenge
  300 (token.rs:20).
- Version info `NETCODE 1.02\0` 13 bytes (lib.rs:141).
- create <= expire: rejected on read when create > expire (token.rs:228-230);
  generation sets expire = create + expire_seconds (token.rs:299-301).
- Up to 32 server addresses (lib.rs:124; range checks token.rs:92, 237).
- User data 256 (lib.rs:121; token.rs:77, 107).
- Timeout seconds carried (token.rs:70, 208); negative disables (token.rs:301,
  server.rs:890-894).
- Private token encrypted with XChaCha20-Poly1305, 24-byte nonce, associated
  data version+protocol+expire (token.rs:25-31, 116-138; crypto.rs:56-81).
- Challenge token encrypted with ChaCha20-Poly1305, no AD, sequence nonce
  (token.rs:166-180).
- Token history 8 x clients (server.rs:243), encryption-manager mappings
  4 x clients (server.rs:50), entry expiry (server.rs:300-305) and single-use
  semantics (server.rs:309-332, 335-337) match STANDARD.md "Connect Token
  History".

## 4. Server

**MATCH (mostly), with divergences.**

- Global sequence seeded at create and at start: server.rs:463 and
  server.rs:498. IMPLEMENTERS.md section 3 requires start to restore the
  floor `2^63`; the port also seeds on create. MATCH.
- Restart floor ordering: `start` sets `min_connect_token_expire_timestamp`
  from `unix_timestamp()` plus the configured maximum lifetime
  (server.rs:492-493) before it can accept requests. MATCH.
- Challenge/denied handling: challenge server.rs:909-933, denied
  server.rs:884-888 and 975-980. MATCH.
- Response accepted only with the mapping's own challenge: the challenge token
  is decrypted with the server challenge key (server.rs:943-952) and the
  client is installed only against the address's encryption mapping
  (server.rs:956-991). MATCH.
- Client timeouts: server.rs:1143-1158. Keep-alive rate 10 Hz: lib.rs:143
  (`PACKET_SEND_RATE = 10.0`) applied server.rs:1131. Redundant disconnect
  count 10: lib.rs:144 applied server.rs:1056. Max clients 256: lib.rs:127
  checked server.rs:477. MATCH to STANDARD.md 419, 550, 556.

**DIVERGENCE D4.1 (allowed) — global sequence reseeded on stop.**
Port server.rs:515 reseeds `global_sequence = 1 << 63` in `stop`, where the C
reference (per the card, and netcode commit dc21b70 in the port's own test
note server.rs:1186-1187) zeroes it and reseeds only in `start`. STANDARD.md
"Nonce Reuse and Server Restarts" says the value while not running is
unspecified and start must restore the floor; reseeding on stop is within
that. The port's test server.rs:1454-1481 pins all three seeds.

**DIVERGENCE D4.2 (allowed) — events polled from a queue, no callbacks.**
Port server.rs:398 (`events: VecDeque<ServerEvent>`) and server.rs:537
(`next_event`) expose connect/disconnect as a drained queue rather than the C
reference's function-pointer callbacks (C callback struct, card cite). This is
a Rust API idiom; the observable behaviour (one connect event, one disconnect
event per transition) is the same. STANDARD.md specifies no callback interface.

**DIVERGENCE D4.3 — server binds one socket; C has dual sockets + address2.**
Port server.rs:433-437 binds a single socket chosen by the family of
`public_address`, and server.rs:844 matches the token's server-address list
against that one `public_address`. C binds both an IPv4 and an IPv6 socket and
carries a second public address (address2) (card cites C 4645, 5084). A client
token naming an IPv6 address while `public_address` is IPv4 can never match
here. This is not in STANDARD.md ("The dedicated server must be on a publicly
accessible IP address and port" assumes a single address). Verdict: DIVERGENCE
that a card would resolve by adding the second socket and address2; recorded
as a QUESTION for the exact C semantics until a C checkout is read.

**DIVERGENCE D4.4 — no loopback clients.** The C reference (1.4.x) can connect
a loopback client without a socket and refuses a loopback connect when the
loopback callback/send function is unset; the port has no loopback client API
at all (the `Server` struct server.rs:381-399 carries no loopback state, and
no `connect_loopback` method exists). Checklist item 4 names loopback clients
and item 6 the refusal rule; both are N/A here. Verdict: DIVERGENCE (feature
absent); a card would add the loopback seam.

## 5. Client

**MATCH (mostly).**

- State machine values -6..3 and predicates: client.rs:23-75 match
  STANDARD.md "Client State Machine" exactly.
- Sequence handling: write then increment client.rs:477-487.
- Next-server-address stepping: client.rs:406-433. Timeouts: client.rs:259-286
  (request, response, connected) and token expiry client.rs:240-248.
- Keys and token use: read key = server-to-client, write key =
  client-to-server (client.rs:222-223); request carries the private data
  (client.rs:444-450); response carries the challenge data (client.rs:454-458).

**QUESTION Q5.1 — sequence advanced when no socket exists.**
`send_packet_to_server` increments `self.sequence` at client.rs:487 before it
selects the socket at client.rs:489-500, so a packet for which no socket of
the right family exists still consumes a sequence number (the packet is not
sent). The card cites C 3330 for the client's send. Gaps in a nonce sequence
are harmless for AEAD and replay, but whether C has the same gap needs the C
checkout. What would settle it: read the C client send path at 3330.

**DIVERGENCE D5.1 (allowed) — `Client::connect` returns `Result`.**
Port client.rs:198 returns `Err(Error::InvalidConnectToken)` and sets the
error state (client.rs:201-207); C's connect returns void. This is the Rust
idiom; the state transition is identical. Recorded as allowed.

## 6. Receive loops and callbacks (C 1.4.6–1.4.8)

**DIVERGENCE D6.1 — a zero-length datagram ends the drain.**
Port socket.rs:67-71 maps `Ok((0, _))` to `return None`, i.e. an empty
datagram is treated the same as "would block". The drain loops
(server.rs:691-695, client.rs:507-524) then stop, leaving any datagrams queued
behind the empty one for the next `update`. C 1.4.6 *skips* empty datagrams
and keeps draining. This is a real behavioural difference on a hostile or
odd input. A card would make `receive_packet` continue past a zero-length
datagram instead of returning None. C line unavailable without a checkout;
recorded against C section 1.4.6.

**DIVERGENCE D6.2 — every drain is unbounded.**
The receive loops (server.rs:691-695, client.rs:507-524) drain until the
socket would block, with no per-update cap. C 1.4.6 caps the number of
datagrams processed per receive call (the card's "receive-cap constants are
absent"; C `NETCODE_MAX_PACKETS_PER_RECEIVE`-style limit). A burst of queued
datagrams therefore costs unbounded work in one `update` here. A card would
add the cap. C line unavailable without a checkout.

**QUESTION Q6.1 — payload slack, address-string buffer, create-error codes 7/8,
loopback refusal, simulator allocation.** These are C 1.4.6–1.4.8 behaviours
that hang off callbacks a port without callbacks does not have. Port payload
read copies the payload exactly (packet.rs:362-368) rather than handing the
application eight bytes of readable slack behind it; the port surfaces
addresses as `SocketAddr` and formats them with `Display`, so the
`NETCODE_MAX_ADDRESS_STRING_LENGTH` fixed-buffer contract has no counterpart;
there is no override-send-and-receive config, so create error codes 7 and 8
do not exist; and there is no network simulator, so the "failing simulator
allocation drops the packet and keeps the queued entry" rule has none either.
What would settle these: a C checkout to read 1.4.6–1.4.8 and decide which are
in scope for a callback-free Rust port.

## 7. Randomness

**MATCH (stronger than C).** Compared `src/crypto.rs` and `src/token.rs`
against IMPLEMENTERS.md section 4.

- Keys and nonces come from the OS RNG: crypto.rs:83-85 (`getrandom::fill`),
  crypto.rs:88-92, token.rs:303-304. There is no path that leaves a key or
  nonce uninitialised: `random_bytes` panics on RNG failure rather than
  returning zeroes or stack contents, so a platform with a stubbed RNG fails
  loudly instead of silently using uninitialised memory.
- Where the wall clock is read: `token::unix_timestamp()` token.rs:262-264, in
  `Server::start` (server.rs:493) and `Server::receive_packets`
  (server.rs:689), `Client::process_packet` (client.rs:536) and
  `generate_connect_token` (token.rs:299).

**DIVERGENCE D7.1 — `unix_timestamp` panics on a pre-1970 clock.**
token.rs:263 uses `.expect("system clock is before 1970")`. The C reference
reads a wall clock that cannot be pre-1970 into an unsigned value without a
panic. A card could saturate to zero instead of panicking.

Whether 1.1.2 is meant to track a particular C `NETCODE_VERSION` is not
recorded anywhere in this tree. What would settle it: read `NETCODE_VERSION`
in the C `netcode.h`/`netcode.c`.

## 9. The port's own interop pin / golden vectors

**QUESTION Q9.1 — the golden vectors name no C commit, and the interop pin

`src/wire_compat.rs:15-17` says the `tests/vectors/*.bin` were produced by a
small program against "the reference C implementation" but names no commit

would settle it: a checkout to `git log` the C reference and compare, plus
regenerating nothing until the standard itself changes.

## KNOWN CANDIDATES — confirmed or refuted

1. **One server socket vs C dual sockets + address2.** CONFIRMED.
   server.rs:433-437, 844; card cites C 4645, 5084. See D4.3.
2. **Events polled from an unbounded queue vs callbacks.** CONFIRMED.
   server.rs:398, 537. See D4.2 (allowed).
3. **`stop` reseeds `global_sequence` where C zeroes it and reseeds in
   `start`.** CONFIRMED. server.rs:515. Allowed by IMPLEMENTERS.md section 3.
   See D4.1.
4. **Receive-cap constants absent.** CONFIRMED. No cap in server.rs:691-695 or
   client.rs:507-524. See D6.2.
5. **IPv6 flow label and scope id zeroed.** CONFIRMED. socket.rs:86-95,
   bytes.rs:123-130. Allowed and documented in CLAUDE.md: the C
   implementation cannot represent either field, so equality would otherwise
   silently drop link-local packets. DIVERGENCE (allowed).
6. **`Server::new` does not normalise `public_address`.** CONFIRMED.
   server.rs:439-444 stores `public_address` as given; only the port is
   patched. A scope id on a link-local public address is kept, so
   `server_addresses.contains(&self.public_address)` (server.rs:844) can
   never equal the normalised address a received packet carries (bytes.rs:129
   / socket.rs:92). Card cites C 4641. This is a BUG-shaped divergence: a
   card would normalise `public_address` through the same
   `normalize_address` path. Port server.rs:439-444 and 844; C 4641 cited.
7. **`unix_timestamp().expect` panics on a pre-1970 clock.** CONFIRMED.
   token.rs:263. See D7.1.
8. **Payload size errors return `Err` where C logs.** CONFIRMED.
   server.rs:543-546, client.rs:290-293. `send_packet` with an empty or
   oversized payload returns `Error::InvalidPayloadSize`; C logs and returns.
   DIVERGENCE (allowed, Rust idiom).
9. **`Client::connect` returns a `Result` where C returns void.** CONFIRMED.
   client.rs:198-230. See D5.1 (allowed).
10. **Client increments its sequence before it knows a socket exists.**
    CONFIRMED. client.rs:487 against 489-502; card cites C 3330. See Q5.1.
11. **C 1.4.7 missing-callback refusals and 1.4.6 payload slack map onto a
    port with no callbacks.** CONFIRMED as N/A. See Q6.1.

are written and committed. The leg did not run: no C checkout is reachable
(JOB.md names none, `NETCODE_C_DIR` is unset). To run it against a checkout of

or after `406e8d28`):

    NETCODE_C_DIR=<checkout> cargo test --test c_differential -- --ignored --test-threads=1

Two limits worth naming, both visible in the files:

- The port's packet reader `netcode::packet::read_packet` and `Packet` are
  `pub(crate)`, so an integration test (a separate crate) cannot build the port
  transcript. The test says this and returns instead of inventing one; producing
  it needs a public socketless seam or a FakeTransport, which is a library
  change this card may not make.
- `tests/c/oracle.c` is written against the reference API names from memory and
  has never been compiled, because no C checkout is here. Expect to adjust the
  include (the card says `#include "netcode.c"` to reach file-local functions;
  the file is written to link netcode.c separately, which is the same idea) and
  the exact struct/function signatures on first run.

Verdict for the leg: **not-done: no C reference reachable**, with the command
above. It is not claimed red-at-base or green.
